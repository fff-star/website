# SACK（选择确认）

> 参考：RFC 2018; Kurose §3.5.4

**选择确认（Selective Acknowledgment, SACK）**是 TCP 的一个选项，在 RFC 2018 中定义。它允许接收方向发送方报告接收到的**非连续数据块**，使发送方在丢包场景下只需重传确实丢失的报文段，而非整个窗口。

## 累积确认的局限

标准 TCP 使用**累积确认**——ACK 值 $n$ 表示序号 $n-1$ 之前的所有数据已收到。在单个报文段丢失后，接收方每收到一个失序报文段就发送重复 ACK。

假设发送方发送了字节序号 0–7999（对应 8 个报文段，每个 1000 字节）。字节 2000–2999（报文段 3）丢失但 3000–7999 成功到达：

- **单段丢失（累积确认 + 失序缓存，即 TCP Reno 默认行为）**：接收方缓存 3000–7999 并重复 ACK 2000。发送方通过 3 dup ACK 快速重传 seq=2000。接收方收到后，累积 ACK 直接跳到 8000——**只重传了一个段**。
- **多段丢失（无 SACK）**：若同一窗口中丢失了多个段（如 2000、3000、6000 各丢一段），发送方在无 SACK 时只能**逐个发现、逐个重传**——每 RTT 通过 dup ACK 定位一个丢段，N 个丢段需要 N 个 RTT 才能全部修复。
- **多段丢失（有 SACK）**：接收方在 ACK 2000 的同时附加 SACK 块，告知「已收到 [3000, 4000) 和 [5000, 6000) 和 [7000, 8000)」。发送方立即知道三个缺失段的确切位置，可以在同一 RTT 内**一次性重传全部**——无需等待逐个发现。

因此 SACK 的核心优势不在单段丢失场景，而在**同一窗口内多个段丢失时的批量重传能力**。这也是它与纯累积确认（需逐个发现缺失段）和纯 GBN（接收方丢弃失序段，可能需要重传整个窗口）的双重区别。

## SACK 的工作方式

SACK 使用 TCP 首部中的 **选项（Options）**字段（TCP 首部最长 40 字节的选项空间）。

SACK 选项包含：
- **SACK-Permitted Option**：在 SYN 中由双方协商，确认双方均支持 SACK
- **SACK Option**：在数据传输阶段由接收方发送，描述收到的非连续数据块

一个 SACK 块（block）包含：
- **左边界（Left Edge）**：接收到的第一个非连续字节的序号
- **右边界（Right Edge）**：接收到的连续块最后一个字节的下一个序号（即结束位置 + 1）

由于 TCP 选项空间有限（最长 40 字节），一个 SACK 报文最多报告 **3–4 个非连续块**。

## SACK 与快速重传的配合

SACK 增强了快速重传机制。当发送方收到 SACK 信息时：

1. 构建**缺失位图**——哪些报文段已确认，哪些缺失
2. 对每个缺失的报文段单独执行快速重传（不等定时器超时，也不限于 3 个重复 ACK 的门槛）
3. 重传只针对实际丢失的报文段，避免不必要的数据重传

TCP 的可靠数据传输由此更接近 SR（选择重传）的行为——在累积确认的基础上，增加了选择性确认的能力。

## SACK 与 SR 的区别

| | 标准 TCP（累积 ACK）| TCP + SACK | SR（选择重传）|
|---|---|---|---|
| ACK 类型 | 累积 ACK | 累积 ACK + SACK 选项 | 每个分组的独立 ACK |
| 定时器 | 单一定时器 | 单一定时器 | 每分组一个定时器 |
| 重传粒度 | 可能重传整个窗口 | 仅重传丢失的报文段 | 仅重传丢失的分组 |
| 接收缓冲 | 按序交付 | 缓存失序块 | 缓存失序分组 |

SACK 在保留 TCP 累积确认框架的基础上，以最小的协议修改（仅增加选项）弥补了最关键的效率缺陷。

## SACK 的局限性

- 仅当双方在 SYN 中协商才启用（实际部署中大部分 TCP 实现支持）
- 选项空间限制使一次最多报告 3–4 个连续块
- 发送方何时可安全地从重传队列中移除已 SACK 的数据，由实现决定，非标准规定
- 在丢失密集场景下（大量短流、极高丢包率），SACK 的改善有限

尽管有局限，SACK 已成为现代 TCP 实现的标准配置，大幅提升了高带宽、高延迟网络中丢包后的恢复效率。
