# QUIC

> 参考：Kurose §3.8（QUIC 补充）、RFC 9000

**QUIC（Quick UDP Internet Connections）**是由 Google 设计的新一代运输层协议，最初于 2012 年部署，2021 年由 IETF 标准化为 RFC 9000。QUIC 运行在 UDP 之上，在应用层实现了可靠性、拥塞控制和安全加密——本质上是将 TCP 与 TLS 的功能合并到单个协议中，同时解决了 TCP 的多个根本性限制。

[[HTTP]] 的第三个主要版本 HTTP/3 基于 QUIC 而不是 TCP。理解 QUIC 对于理解现代网络协议栈的演进至关重要。

## QUIC 的核心特征

### 连接 ID：脱离四元组绑定

TCP 连接由**四元组**（源 IP + 源端口 + 目的 IP + 目的端口）唯一标识。这意味着：
- 客户端 IP 地址变化（如 WiFi → 蜂窝网络切换）→ TCP 连接断开
- 需要重新三次握手和 TLS 握手 → 显著延迟

QUIC 使用**连接 ID（Connection ID）**来标识连接——这是一个不透明的可变长度标识符（0-20 字节，常见部署为 64 比特），独立于 IP 地址和端口。即使底层 IP 地址发生变化，只要连接 ID 不变，QUIC 连接就可以无缝继续。这实现了**连接迁移（Connection Migration）**——设备从 WiFi 切换到蜂窝网络时，进行中的 QUIC 连接不中断。

### 流复用：彻底消除队首阻塞

TCP 提供单个有序字节流。HTTP/2 在此之上用帧复用实现多流，但当 TCP 丢失一个分组时，所有流都被阻塞——TCP 必须重传丢失的分组并按序交付，即使该分组只属于一个流。这称为**TCP 队首阻塞（Head-of-Line Blocking）**。

QUIC 在传输层本身支持**多流（streams）**——一个 QUIC 连接内可承载数十个独立的流，每个流有自己的序号和可靠性保证：
- 流 A 丢失的分组只有流 A 等待重传
- 流 B、C、D 完全不受影响，继续交付数据到应用层

这是 HTTP/3 相对于 HTTP/2 的最大改进。

### 0-RTT 与 1-RTT 握手

QUIC 将传输握手与加密握手合并：

| 场景              | QUIC 握手                                                                          | TCP + TLS 1.3 等效                         |
| --------------- | -------------------------------------------------------------------------------- | ---------------------------------------- |
| **首次连接**        | **1-RTT**：客户端发送 ClientHello（含 QUIC 和 TLS 参数），服务器在一个往返中回复 ServerHello + 加密扩展 + 数据 | 1-RTT（TCP 握手） + 1-RTT（TLS 握手） = 2-RTT    |
| **曾连接过（0-RTT）** | **0-RTT**：客户端使用之前缓存的服务器参数，在握手完成的同时直接发送应用数据                                       | 0-RTT（TLS 1.3 会话恢复，但仍需先完成 TCP 握手）= 1-RTT |

首次连接 1-RTT vs TCP+TLS 的 2-RTT 节约了一个往返。复用连接 0-RTT 比 TCP+TLS 的 1-RTT 更快。

### 内置 TLS 1.3 加密

QUIC **强制加密所有数据**（借鉴 TLS 1.3）：
- 大多数 QUIC 分组（包括 ACK）在传输层就被加密
- 中间设备（middlebox）无法窥探或干扰 QUIC 的内部状态（如连接 ID、流 ID、ACK）
- 防止了 TCP 面临的"僵化（ossification）"问题——中间设备假设 TCP 首部的某些字段不变，导致 TCP 扩展难以部署

QUIC 使用两个级别的加密：
- **初始加密**：用初始密钥保护握手消息
- **握手加密**：握手完成后的密钥，保护应用数据

### 改进的丢包恢复

QUIC 的 ACK 机制相比 TCP 有显著改进：
- **单调递增的分组号（Packet Number）**：TCP 的序号基于字节流，重传同一数据使用相同序号，导致接收方无法区分 ACK 对应的是原始传输还是重传（重传歧义，retransmission ambiguity）。QUIC 的分组号始终递增——即使重传同一数据，也使用新分组号。接收方因此可以精确测量每个传输的 RTT，消除重传歧义。
- **更精细的 ACK 块**：QUIC 的 ACK 帧可报告最多 256 个分组范围的接收情况，比 TCP SACK（最多 3-4 个块）更精确。
- **ACK 延迟信息**：QUIC ACK 帧包含接收方处理 ACK 的延迟，发送方可以更准确地计算真实的网络 RTT。

## QUIC 与 TCP 的详细对比

|              | TCP + TLS 1.3                     | QUIC                |
| ------------ | --------------------------------- | ------------------- |
| **底层协议**     | IP（协议号 6）                         | UDP（协议号 17）         |
| **连接标识**     | 四元组（IP + 端口）                      | 连接 ID（64 比特，独立于 IP） |
| **握手延迟（首次）** | 2-RTT（TCP 握手 + TLS 握手）            | 1-RTT               |
| **握手延迟（复用）** | 1-RTT（TCP 握手 + TLS 0-RTT）         | 0-RTT               |
| **流复用**      | HTTP/2 帧复用（TCP 层队首阻塞）             | 原生多流（无跨流阻塞）         |
| **加密范围**     | TLS 仅加密有效载荷                       | 加密几乎所有内容（包括 ACK）    |
| **连接迁移**     | 不支持（IP 变则连接断）                     | 支持（连接 ID 机制）        |
| **重传歧义**     | 存在（无法区分原始与重传）                     | 消除（分组号始终递增）         |
| **部署方式**     | 内核实现                              | 用户空间实现（基于 UDP）      |
| **中间设备兼容性**  | 好（但易僵化）                           | 需 UDP 不被阻止          |
| **拥塞控制**     | 内核算法（CUBIC 等）                     | 用户空间可插拔             |
| **标准化**      | RFC 793 (TCP), RFC 8446 (TLS 1.3) | RFC 9000            |

## 用户空间实现的意义

QUIC 运行在用户空间（而非操作系统内核），这意味着：
- **快速迭代**：协议升级只需更新应用程序（如浏览器），无需等待操作系统内核更新
- **可插拔拥塞控制**：应用可以为特定场景选择最适合的拥塞控制算法
- **跨平台一致性**：同样的 QUIC 实现在所有操作系统上行为一致

这也是 TCP 演进缓慢的根本原因之一——内核中的 TCP 栈更新需要跨多个操作系统的协调，耗时数年。QUIC 避免了这个问题。

## QUIC 的采用现状

- Google 的所有服务（YouTube、Search、Gmail）通过 QUIC 交付超过 95% 的流量
- Facebook、Cloudflare、Akamai 等主要的 CDN 和内容提供商已全面部署 QUIC
- 所有主流浏览器（Chrome、Firefox、Edge、Safari）均支持 QUIC/HTTP/3
- HTTP/3（基于 QUIC）占全球 Web 流量的比例持续增长
