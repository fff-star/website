# 应用层协议原理

> 参考：Kurose §2.1

网络应用是因特网存在的理由——如果没有可用的应用，就不会有支持它们的网络基础设施和协议。自因特网诞生以来，出现了众多有用且有趣的应用，它们推动了因特网的成功。本章研究应用层协议的基本原理和具体协议：先讨论网络应用的共同架构和设计原则，然后逐一深入 HTTP（Web）、SMTP/POP3/IMAP（电子邮件）、DNS（域名系统）、P2P 文件分发和视频流。

## 网络应用的体系结构

在开发网络应用之前，首先要选择**应用体系结构（application architecture）**。应用体系结构不同于网络体系结构（如五层因特网协议栈）——前者由应用开发者设计，规定了应用如何在各种端系统上组织。主要有两种主流体系结构：

### 客户-服务器体系结构（C/S）

在**客户-服务器（Client-Server, C/S）体系结构**中，有一个**始终在线**的主机，称为**服务器**，它服务于来自许多其他主机（**客户端**）的请求。关键特征：

- **服务器有固定的、周知的 IP 地址**，客户端可以随时向其发送分组
- **客户端之间不直接通信**——所有通信通过服务器中介
- 单个服务器主机可能无法满足所有客户端的请求 → 配备大量主机的**数据中心（data center）** 被用来创建强大的虚拟服务器

经典的 C/S 应用包括 Web、FTP、Telnet 和电子邮件。

### P2P 体系结构

在 **P2P（Peer-to-Peer）体系结构**中，应用在**对等方（peer）**之间直接通信，不通过专门的服务器。对等方是用户控制的端系统（笔记本、智能手机等），不依赖数据中心中的专用服务器。P2P 体系结构的关键优势是**自扩展性（self-scalability）**——每个对等方同时是消费者（下载数据）和分发者（上传数据），随着对等方数量增加，系统的服务能力也自动增强。

P2P 面临的挑战包括 ISP 友好性（大多数 ISP 为非对称带宽设计，上行速率远低于下行速率）、安全性和激励问题（如何鼓励对等方贡献资源）。

## 进程通信

网络应用由**进程（process）** 构成——运行在端系统上的程序。不同端系统上的进程通过跨越计算机网络的**报文（message）** 交换进行通信。

### 客户与服务器进程

对于每对通信的进程，通常将其中一个标记为**客户（client）**，另一个标记为**服务器（server）**：

- **客户进程**：发起通信的一方
- **服务器进程**：等待被联系的一方

例如在 Web 场景中，浏览器（在用户主机上运行的客户端进程）向 Web 服务器进程发起通信。

### 套接字

进程通过**套接字（socket）**的软件接口向网络发送报文和从网络接收报文。套接字是应用层与运输层之间的**接口（API）**——也称为应用与网络之间的**应用程序编程接口（API）**。应用开发者可以控制套接字在应用层一侧的所有内容，但对运输层一侧几乎无法控制（只能选择运输协议和可能调整几个参数）。

类比：套接字类似于一道门——发送进程将报文推出这道门，依赖门另一侧的运输基础设施将报文交付到目的进程的门口。一端的进程将报文推出套接字，另一端进程从其套接字接收报文。

### 进程寻址

为了将报文交付到目的进程，需要两个信息：

1. **主机地址**：由 IP 地址（IP address）标识。IPv4 地址为 32 比特，IPv6 地址为 128 比特
2. **进程标识**：在主机内由**端口号（port number）** 标识

知名端口号的例子：Web 服务器用端口 80（[[HTTP]]），SMTP 邮件服务器用端口 25（[[电子邮件与SMTP]]）。

## 运输服务

应用可用的运输服务可以从以下四个维度分类：

### 可靠数据传输

- **可靠传输**：协议保证数据正确、完整地按序到达目的地。需要可靠性的应用——如电子邮件、文件传输、Web 文档传输——使用 [[TCP概述|TCP]]。
- **不可靠传输（容忍丢失）**：协议不保证交付。容忍丢失的应用（如音频/视频流、在线游戏）可以使用 [[UDP]]。

### 吞吐量

- **带宽敏感应用（bandwidth-sensitive）**：有特定的吞吐量要求（如 VoIP 需要 32 kbps 以上，视频流需要数百 kbps 到数 Mbps）
- **弹性应用（elastic）**：可利用任何可用的吞吐量（如电子邮件、文件传输、Web 传输）

### 定时

- **实时交互应用**：要求低延迟（如 VoIP 中单向延迟需小于 150 ms 才能良好交互，在线游戏则更严格）
- 非实时应用：对端到端延迟没有严格约束

### 安全性

运输协议可以为应用提供安全性服务，如数据加密、数据完整性、端点认证。TCP 和 UDP 本身不提供加密。因特网中通过[[TLS|运输层安全协议（TLS，Transport Layer Security）]]在应用层进行加密——TLS 强化了 TCP，提供机密性、数据完整性和端点认证。

## 常见因特网应用的运输服务要求

| 应用 | 数据丢失 | 吞吐量 | 时间敏感 |
|------|---------|--------|---------|
| 文件传输 | 不允许丢失 | 弹性 | 否 |
| 电子邮件 | 不允许丢失 | 弹性 | 否 |
| Web 文档 | 不允许丢失 | 弹性 | 否 |
| 实时音频/视频 | 容忍丢失 | 音频：Kbps–Mbps 视频：Kbps–10+Mbps | 是（<~150 ms） |
| 存储音频/视频 | 容忍丢失 | 同上 | 是（<~几秒） |
| 交互式游戏 | 容忍丢失 | Kbps 以上 | 是（<~100 ms） |
| 即时消息 | 不允许丢失 | 弹性 | 是和否 |

## 应用层协议

**应用层协议（Application-Layer Protocol）** 定义了在不同端系统上的应用进程如何相互传递报文。它定义了：

- **交换报文的类型**：请求报文、响应报文
- **各种报文类型的语法**：报文中的字段及其分隔方式
- **字段的语义**：字段中信息的含义
- **何时和如何发送报文以及响应报文的规则**

某些应用层协议由 RFC 定义，因此处于公共领域（如 HTTP、SMTP）。其他应用（如 Skype、许多 P2P 文件共享系统）使用专用应用层协议，不公开。

应用层协议只是网络应用的一部分——例如 Web 应用由 HTTP（应用层协议）、Web 浏览器（用户代理）、Web 服务器和 HTML（文档格式）等多个组件组成。
