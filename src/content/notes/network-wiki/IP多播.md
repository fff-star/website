# IP 多播

> 参考：Kurose §4.7

**IP 多播（IP Multicast）** 允许将单个 IP 数据报从一台源主机交付给网络中 **一组接收方**。与单播（unicast，一对一）和广播（broadcast，一对所有）不同，多播实现了一对多的高效数据传输——源只需发送一份副本，由网络中的路由器在必要时复制并转发给所有组成员。

## 多播的应用场景

| 应用 | 描述 | 带宽特征 |
|------|------|---------|
| 流媒体直播 | 体育赛事、音乐会的实时网络广播 | 高带宽、长期 |
| 软件更新 | 向数据中心中数千台服务器同时分发新版本 | 高带宽、一次性 |
| IPTV | IP 电视向数百万用户组播频道 | 高带宽、持续 |
| 股票行情 | 实时股票价格广播到交易终端 | 低带宽、持续 |
| 视频会议 | 多方实时音视频通信 | 中等带宽、实时 |

## 多播地址

### IP 多播地址（第 3 层）

IPv4 多播使用 **D 类地址**（RFC 1112）：前缀为 `1110` 的地址，即 `224.0.0.0/4`（224.0.0.0 – 239.255.255.255）。

| 多播地址范围 | 用途 |
|-------------|------|
| 224.0.0.0 – 224.0.0.255 | 链路本地多播（仅在同一子网内传播，路由器不转发） |
| 224.0.1.0 – 238.255.255.255 | 全球范围多播（可跨因特网路由） |
| 239.0.0.0 – 239.255.255.255 | 管理范围多播（限于特定管理域，类似私有 IP） |

知名多播地址举例：
- `224.0.0.1`：子网上所有系统（All Hosts）
- `224.0.0.2`：子网上所有路由器（All Routers）
- `224.0.0.5`：所有 OSPF 路由器
- `224.0.0.6`：OSPF 指定路由器（DR）

IPv6 多播使用 `FF00::/8` 前缀。

### MAC 层多播地址（第 2 层）

在以太网等广播链路中，IP 多播地址需要映射到链路层多播 MAC 地址。对于以太网：
- 多播 MAC 地址以 `01:00:5E` 开头（OUI 的高 25 比特固定为此值）
- IP 多播地址的低 23 比特直接映射到 MAC 多播地址的低 23 比特

由于 IPv4 多播地址有 28 个有意义比特（D 类地址前 4 位固定为 `1110`），但以太网多播 MAC 只能容纳 23 比特，意味着 5 个比特被丢弃。因此 $2^5 = 32$ 个不同的 IP 多播地址会映射到**同一个**以太网多播 MAC 地址。

**后果与补救——IP 层的二次过滤**：

网卡收到帧时只看目的 MAC 地址——只要 MAC 匹配自己监听的某个多播 MAC，就收下帧交给 IP 层。由于 32 对 1 的映射关系，网卡会**多收一些不属于自己组的帧**。因此 IP 层收到数据报后必须做一次额外检查：

```
链路层（网卡）:
  "目的 MAC 是 01:00:5E:57:91:E6？和我监听的 MAC 匹配？ → 收下"

IP 层（协议栈）:
  "目的 IP 是 224.215.145.230？我确实加入了这个多播组吗？
   ├── 是 → 交付给上层（TCP/UDP）  ✓
   └── 不是 → 静默丢弃（这只是那 31 个共享同一 MAC 的组中
              某个与我无关的流量）    ✗"
```

一个具体例子：主机加入了多播组 `224.0.1.1`（MAC = `01:00:5E:00:01:01`）。`238.0.1.1`（另一个完全无关的组）映射到的 MAC 也是 `01:00:5E:00:01:01`。网卡无法区分，会把发给 `238.0.1.1` 的帧一并收下。IP 层检查到目的 IP 是 `238.0.1.1`，而自己从未用 IGMP 加入过这个组 → **丢弃**。整个过程对上层应用透明。

## IGMP：因特网组管理协议

**IGMP（Internet Group Management Protocol）** 运行在主机与其直接相连的路由器之间。主机使用 IGMP 通知本地路由器它要加入或离开某个多播组。IGMP 报文封装在 IP 数据报中（协议号 2）。

IGMP 有三个版本：

### IGMPv1（RFC 1112）

- **成员查询（Membership Query）**：路由器周期性（默认 60 秒）向 224.0.0.1（子网所有主机）发送查询
- **成员报告（Membership Report）**：主机发送报告表明加入组，或响应查询
- **静默离开**：主机不再发送报告即离开

### IGMPv2（RFC 2236）

在 IGMPv1 基础上增加：
- **离开组（Leave Group）**：主机显式告知路由器自己离开，减少离开延迟
- **组特定查询（Group-Specific Query）**：路由器只查询某个特定组的成员状态
- **查询/响应最大响应时间**：可由路由器配置

### IGMPv3（RFC 3376）

关键增强——**源特定多播（Source-Specific Multicast, SSM）**：
- 主机可以指定它想接收**来自特定源**的流量
- 使用 INCLUDE/EXCLUDE 源列表
- 使接收方能过滤恶意源发送的多播数据

## 多播路由算法

多播路由的目标是构建一棵覆盖所有组成员的**多播树（Multicast Tree）**：

### 反向路径转发（RPF, Reverse Path Forwarding）

RPF 是多播路由的基础机制：路由器收到多播分组时，检查分组是否从**到达源的最短路径的接口**进入：
- 如果是——**泛洪**到所有其他接口
- 如果不是——**丢弃**该分组

RPF 确保每个分组在网络中沿源树向下传播，而不会形成环路。

### DVMRP（Distance Vector Multicast Routing Protocol）

DVMRP 是最早的多播路由协议，使用**扩散-剪枝（Flood-and-Prune）**方式：
1. 源初始向全网泛洪多播数据
2. 无组成员的路由器向上游发送**剪枝（Prune）**消息
3. 剪枝有超时时间，超时后需重新泛洪和剪枝

DVMRP 使用类似 [[RIP]] 的跳数度量。第一个广泛使用的多播路由协议——因特网 **MBone**（Multicast Backbone）即基于 DVMRP。

### PIM-DM（Protocol Independent Multicast — Dense Mode）

PIM-DM 也使用扩散-剪枝模型，适合组成员密集分布的场景。其名称"协议无关"指它不依赖特定的单播路由协议——使用单播路由表中的任何路径进行 RPF 检查。

### PIM-SM（Protocol Independent Multicast — Sparse Mode）

PIM-SM 是当前多播部署的主流协议，适合组成员稀疏分布（如因特网）。不使用扩散-剪枝，而使用**显式加入（Explicit Join）**：

1. 每个多播组有一个**汇聚点（Rendezvous Point, RP）**——网络中某个已知的路由器
2. 接收方通过向 RP 发送**PIM Join**消息显式加入组
3. 源向 RP 单播多播数据，RP 沿共享树转发给组成员
4. 可选：当数据速率超过阈值时，从共享树切换到**最短路径树（Shortest Path Tree, SPT）**以优化性能

PIM-SM 的共享树使用**(*,G)**路由状态（任何源到组 G），切换后使用**(S,G)**路由状态（源 S 到组 G）。

### SSM（Source-Specific Multicast）

SSM 是最简化的多播模型：接收方必须知道源的 IP 地址，使用 **(S,G)** 通道而非 **(*,G)** 组。由于只有单个源，不需要 RP，架构简单。依赖 IGMPv3 进行源过滤。典型应用：IPTV（用户只需知道频道源的 IP）。

## 多播 vs 广播 vs 单播

| | 单播 (Unicast) | 广播 (Broadcast) | 多播 (Multicast) |
|---|--------------|----------------|-----------------|
| 接收方数量 | 1 | 子网内所有 | 任意数量的指定组 |
| 源发送的副本数 | N (每个接收方一份) | 1 | 1 |
| 网络带宽效率 | 低（重复传输） | 中等（全域泛洪） | 高（按需复制） |
| 路由器是否转发 | 是 | 否（限于子网） | 是（仅沿多播树） |
| IP 地址范围 | A/B/C 类 | 子网定向广播/255.255.255.255 | 224.0.0.0/4 (D 类) |
| 典型应用 | Web、邮件 | ARP 请求、DHCP 发现 | IPTV、多方会议 |
