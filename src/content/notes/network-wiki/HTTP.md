# HTTP（超文本传输协议）

> 参考：Kurose §2.2

**超文本传输协议（HyperText Transfer Protocol, HTTP）** 是 Web 的应用层协议。HTTP 由两个程序实现：客户端程序（Web 浏览器，如 Chrome、Firefox）和服务器程序（Web 服务器，如 Apache、Nginx），它们运行在不同端系统上，通过交换 HTTP 报文进行通信。HTTP 定义了 Web 客户端如何向 Web 服务器请求 Web 页面，以及服务器如何将 Web 页面传送给客户端。

## 基本概念

一个 **Web 页面（Web page）** 由**对象（object）** 组成——对象只是一个文件（如 HTML 文件、JPEG 图片、Java 小程序、视频片段），且可通过一个 URL 寻址。多数 Web 页面由一个**基本 HTML 文件（base HTML file）** 和若干个引用对象组成。

每个 URL 由两部分组成：存放对象的**服务器主机名**和对象的**路径名**。例如 `http://www.someSchool.edu/someDepartment/picture.gif` 中，`www.someSchool.edu` 是主机名，`/someDepartment/picture.gif` 是路径名。

## HTTP 的运输层

HTTP 使用 **TCP** 作为其底层运输协议——HTTP 客户端首先通过 TCP 与服务器建立连接。连接建立后，客户端和服务器通过套接字接口访问 TCP。HTTP 默认使用 TCP 端口 **80**，HTTPS（HTTP over TLS）使用端口 **443**。

HTTP 是**无状态协议（stateless protocol）**——服务器不存储关于客户端的任何状态信息。如果客户端在短时间内两次请求同一个对象，服务器不会因为刚才提供了该对象而不响应；它重新发送该对象，仿佛已经遗忘了之前做过的事。

## HTTP 版本演进

HTTP 从 1991 年的 0.9 版到 2022 年的 HTTP/3，经历了四次重大变革。核心驱动力是**减少延迟**和**提高带宽利用率**。

### HTTP/1.0 — 每请求一个连接

HTTP/1.0（RFC 1945, 1996）奠定了请求-响应的基本模型，**默认使用非持久连接**：每个请求对象需要新建一个 TCP 连接。获取一个含 4 个图片的简单网页，需要建立 5 次 TCP 连接，总耗时 $10 \times RTT$（参见 [[HTTP持久连接与非持久连接]]）。HTTP/1.0 也可通过 `Connection: keep-alive` 首部协商持久连接，但需要客户端和服务器双方显式支持，并非规范强制要求。

### HTTP/1.1 — 持久连接与流水线

HTTP/1.1（RFC 2616, 1997; RFC 7230, 2014）的核心改进：

- **默认持久连接**：TCP 连接在响应后保持打开，可复用，减少重复握手开销
- **流水线（Pipelining，可选）**：无需等待前一个请求的响应即可连续发送后续请求。但由于**队首阻塞（HOL Blocking）**——第一个大对象处理缓慢会堵住后续所有响应——实践中大多数浏览器默认关闭流水线
- **Host 首部（必需）**：使得一台服务器托管多个 Web 站点成为可能（虚拟主机）
- **分块传输编码（Chunked Transfer Encoding）**：允许服务器逐块发送动态生成的内容，无需预先知悉总长度
- **更多缓存控制**：`Cache-Control` 首部取代了 HTTP/1.0 简单的 `Expires`

### HTTP/2 — 二进制多路复用

HTTP/2（RFC 7540, 2015）在不改语义的前提下变革了传输方式：

- **二进制分帧**：HTTP 报文被拆分为二进制帧（frame），帧之间可交错传输，同一流的帧按序号重组。文本协议变成了二进制协议。
- **多路复用（Multiplexing）**：单个 TCP 连接上同时交错传输多个请求-响应对。请求 A 的帧和请求 B 的帧可以交替发送，接收方按流 ID 分发。这消除了 HTTP/1.1 **应用层的**队首阻塞——一个慢对象不会再堵住后面的对象。
- **服务器推送（Server Push）**：服务器预测客户端需求，主动将 CSS/JS/图片推送给客户端（无需等待请求）
- **首部压缩（HPACK）**：HTTP 首部在请求间大量重复。HPACK 用静态/动态字典 + Huffman 编码压缩首部，典型节省 30–60% 带宽
- **流优先级**：客户端可标记关键资源（如 CSS），服务器优先发送，优化首屏渲染

**限制**：HTTP/2 仍使用 TCP 传输层。当一个 TCP 段丢失时，TCP 必须按序交付，**所有流全部阻塞**——这是 TCP 层的队首阻塞，HTTP/2 再多路复用也无能为力。

### HTTP/3 — QUIC 替代 TCP

HTTP/3（RFC 9114, 2022）用 **QUIC**（Quick UDP Internet Connections）替代 TCP 作为传输层。QUIC 运行在 UDP 之上，在应用层实现了可靠性、拥塞控制和安全加密：

- **彻底消除队首阻塞**：QUIC 中各流独立——流 A 的丢包只阻塞流 A，流 B 继续传输。这是对 HTTP/2 的最大改进。
- **0-RTT 连接建立**：曾连接过的客户端可复用之前协商的参数，在握手完成的同一时刻就开始发送数据。首次连接 1-RTT（TLS + QUIC 握手合并），之后 0-RTT。
- **连接迁移**：QUIC 连接由**连接 ID** 标识，而非传统 TCP 的四元组（源 IP + 目的 IP + 源端口 + 目的端口）。WiFi → 蜂窝网络切换时，连接不中断，无需重建 TCP 和 TLS。
- **内置 TLS 1.3**：QUIC 强制加密所有数据（包括 ACK 包），中间设备无法窥探或干扰。

目前 HTTP/3 已被主流浏览器和大型服务（Google、YouTube、Facebook、Cloudflare）全面部署。

### 四版对比总表

|       | HTTP/1.0 | HTTP/1.1               | HTTP/2           | HTTP/3              |
| ----- | -------- | ---------------------- | ---------------- | ------------------- |
| 年份    | 1996     | 1997                   | 2015             | 2022                |
| 传输层   | TCP      | TCP                    | TCP              | QUIC (UDP)          |
| 连接方式  | 每请求新建    | 持久复用                   | 单 TCP 连接         | 单 QUIC 连接           |
| 报文格式  | 文本       | 文本                     | 二进制帧             | 二进制帧                |
| 多路复用  | 无        | 流水线（理论，有 HOL Blocking） | 多路复用（应用层 HOL 解决） | 多路复用（TCP 层 HOL 也解决） |
| 服务器推送 | 无        | 无                      | 支持               | 支持                  |
| 首部压缩  | 无        | 无                      | HPACK            | QPACK               |
| TLS   | 可选       | 可选                     | 可选（实际上常用）        | **强制**（内置）          |
| 连接迁移  | 不支持      | 不支持                    | 不支持              | 支持                  |
| 0-RTT | 无        | 无                      | 无                | 支持，重连可 0-RTT        |
