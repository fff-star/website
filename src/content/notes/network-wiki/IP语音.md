# IP 语音

> 参考：Kurose §9.3

**IP 语音（Voice over IP, VoIP）**是会话式多媒体应用的代表——通过分组交换网络传输实时双向语音。VoIP 对网络的**时延**和**丢包**极为敏感，必须在尽力而为的 IP 网络上克服若干重大挑战。

## 尽力而为 IP 服务的局限

IP 网络提供尽力而为（best-effort）服务——不保证带宽、时延和丢包率。这对 VoIP 造成三个核心问题：

| 问题 | 原因 | 对语音质量的影响 |
|------|------|-----------------|
| **丢包** | 路由器排队溢出 | 语音出现间隙、断音 |
| **端到端延迟** | 传播+传输+排队+处理时延 | >150 ms 时人耳可感知延迟，>400 ms 时自然对话困难 |
| **时延抖动（Jitter）** | 各分组经历的排队时延不同 | 分组到达间隔不均匀，直接播放会导致声音断续 |

## 去抖动（Removing Jitter）

### 问题

发送方以固定间隔（如每 20 ms）生成语音块并发送。但分组经历不同的网络延迟，到达时间不均匀——有些提前到达，有些延迟到达。如果接收方**立即播放**每个到达的分组，语音会因间隔不规则而失真。

### 方案：播放延迟（Playout Delay）

接收方不立即播放，而是将到达的语音块先存入**去抖动缓冲区（jitter buffer）**，然后以固定速率从缓冲区取出播放。这结合了两种机制：

- **序号（Sequence Number）**：发送方为每个块打上递增序号，接收方据此恢复正确顺序（解决乱序）
- **时间戳（Timestamp）**：每个块携带采样时刻，接收方据此确定正确的播放时间点（解决抖动）

### 固定播放延迟 vs 自适应播放延迟

| 方案 | 方式 | 优点 | 缺点 |
|------|------|------|------|
| **固定播放延迟** | 接收方始终使用固定的播放延迟 $q$（如 150 ms） | 实现简单 | 若实际延迟经常超过 $q$ 则大量分组因"迟到"被丢弃；若延迟远低于 $q$ 则不必要的额外延迟 |
| **自适应播放延迟** | 接收方根据测量的网络延迟动态调整 $q$ | 平衡丢包率和延迟 | 实现更复杂；播放延迟变化可能导致语音出现人工痕迹 |

自适应播放延迟的工作原理：
1. 为每个接收到的分组测量网络延迟 $d_i$（发送时间戳与接收时间的差值）
2. 计算平均延迟 $\bar{d}$ 和偏差 $v$
3. 将播放延迟设为 $q = \bar{d} + 4v$（确保覆盖绝大部分正常波动）
4. 仅在静默期或语音间隙调整播放延迟，避免可感知的变化

## 丢包恢复

VoIP 通常使用 UDP 传输（TCP 重传的延迟不可接受）。丢包率在 1%–20% 之间时语音质量显著下降。恢复方法分为三类：

### 前向纠错（Forward Error Correction, FEC）

在发送端添加冗余信息，使接收方可以从收到的数据中恢复丢失的分组。

**简单 FEC**：每个冗余块是前 $n$ 个块的 XOR 结果。若 $n$ 个块中丢失一个，可以通过 XOR 恢复。代价是带宽增加 $1/n$，端到端延迟增加（接收方必须等待 $n+1$ 个块到达）。

**低比特率编码 FEC**：将第 $n$ 个块的**低质量版本**附加在第 $n+1$ 个块之后。如果第 $n$ 个块丢失，接收方至少可以用低质量版本填充，而非出现静音。代价是每个块增加低质量副本的额外带宽。

### 交织（Interleaving）

发送方在传输前**重新排序**语音数据单元（如将连续的语音段交错排列），接收方收到后恢复原始顺序：

- 原始顺序：1, 2, 3, 4, 5, 6, 7, 8, ...
- 交织后发送：1, 4, 7, 2, 5, 8, 3, 6, ...

好处：如果连续的分组（如 4, 7, 2）连续丢失，恢复后丢失的单元散布在序列中（小间隙而非大块丢失），人耳对小而分散的丢失远不如对大段缺失敏感。

代价：增加了端到端延迟（接收方必须等待足够多的交织块到达后才能恢复）。

### 差错掩盖（Error Concealment）

不恢复丢失的数据，而是**掩盖**丢失的影响——生成类似丢失分组的替代内容。简单方式包括：
- 用**前一个分组**重复替代丢失分组（简单的包重复）
- 通过**插值**从前后分组推导出替代分组（更复杂但效果更好）

## 案例研究：Skype

Skype 是 VoIP 的经典案例，其协议设计体现了对 NAT 穿透和自适应质量的深度考虑：

- **P2P 架构**：Skype 客户端组织为 P2P 覆盖网络（非 C/S），使用类似 Kazaa/FastTrack 的技术
- **编解码器**：支持多种语音编解码器，典型比特率为 8–32 Kbps
- **FEC 与自适应**：根据网络条件动态调整 FEC 冗余量和使用哪个编解码器
- **NAT 穿越**：客户端使用 STUN 和 relay 技术穿越 [[NAT]]（Skype 的对等节点可充当中继）
- **加密**：所有语音和控制通信均加密
- **TCP 备用**：默认使用 UDP；若 UDP 被防火墙阻止，自动回退到 TCP
