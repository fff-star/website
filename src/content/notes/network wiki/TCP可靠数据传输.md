# TCP 可靠数据传输

> 参考：Kurose §3.5.2–§3.5.4

TCP 在 IP 提供的不可靠服务之上创建了**可靠数据传输服务**。TCP 的可靠数据传输服务确保：从发送方应用进程传递到 TCP 发送缓冲区的数据流，最终会无损、无重复、按序地出现在接收方 TCP 接收缓冲区中，交付给接收方应用进程。

## TCP 可靠数据传输的机制

TCP 使用了以下机制的巧妙组合：

- **序号**：基于字节流的序号，使接收方能检测丢失和重排
- **确认**：接收方对已正确接收的字节发送 ACK
- **累积确认**：ACK $n$ 确认序号不超过 $n-1$ 的所有字节
- **单个重传定时器**：TCP 对最旧未确认字节维护**一个定时器**
- **超时重传**：超时后重传最旧未确认报文段
- **快速重传**：收到 3 个重复 ACK 后立即重传（不等定时器超时）
- **混合 SR/GBN 特性**：TCP 使用累积确认（类似 GBN），但也缓存失序报文段（类似 SR）
- **发送窗口**：上述所有机制都通过一个滑动窗口来协调执行

## TCP 发送窗口

TCP 发送方维护一个**发送窗口（send window）**——这是发送方在任意时刻允许"已发出但未确认"的最大数据量。可靠传输、流量控制、拥塞控制三种机制最终都通过这个窗口来执行：

$$\text{有效发送窗口} = \min(\text{cwnd}, \text{rwnd})$$

- **cwnd**（拥塞窗口）：发送方自行估算的、网络能承受的数据量
- **rwnd**（接收窗口）：接收方在 ACK 中通告的、自身缓冲区的剩余空间

发送窗口确保 `cwnd` 和 `rwnd` 中**更紧的那个约束**被遵守。网络拥塞时 cwnd 更小，窗口由拥塞控制主导；接收方处理慢时 rwnd 更小，窗口由流量控制主导。

### TCP 发送方与接收方维护的变量

TCP 连接的两端各自维护各自的变量。以下按照教科书中的命名给出。

**发送方变量**（Kurose §3.5.4–§3.5.5, §3.7）：

| 变量 | 来源 | 含义 |
|------|------|------|
| **SendBase** | §3.5.4 | 最旧未确认字节的序号（the sequence number of the oldest unacknowledged byte）。参见 [[#发送方的事件\|下面的 SendBase 说明]] |
| **LastByteSent** | §3.5.5 | 发送方已发出（放入网络）的最后一个字节 |
| **LastByteAcked** | §3.5.5 | 已被接收方累积确认的最后一个字节——从收到的 ACK 确认号 $y$ 推导：`= y − 1` |

> **`SendBase` 与 `LastByteAcked` 的关系**：`SendBase = LastByteAcked + 1`——两者标定同一条边界（已确认区域与未确认区域的分界），只是从两侧标注。§3.5.4 使用 `SendBase` 描述可靠传输机制；§3.5.5 使用 `LastByteAcked` 描述流量控制不等式。

**接收方变量**（Kurose §3.5.5）：

| 变量 | 含义 |
|------|------|
| **LastByteRead** | 应用进程从 TCP 接收缓冲区中读取的最后一个字节 |
| **LastByteRcvd** | 从网络到达并已放入 TCP 接收缓冲区的最后一个字节 |

> **§3.5.5 的简化假设**：教科书在讨论流量控制时明确假设 *"the TCP receiver discards out-of-order segments"*（丢弃失序报文段）。在此假设下没有缺口，`LastByteRcvd` 始终指向连续数据的末尾，`rwnd = RcvBuffer − (LastByteRcvd − LastByteRead)` 是精确的。但 §3.5.4 的 ACK 生成规则（Table 3.2）又允许缓存失序报文段（Table 3.2 note），导致 `rwnd` 公式在真实实现中需按实际存储的失序字节量调整——教科书在不同章节取了不同的简化级别。

### 发送缓冲区：四个区域

这些变量将**发送缓冲区**划分为四个区域：

```
发送缓冲区（应用写入的数据）
┌────────────────┬──────────────────┬──────────────────┬──────────────────┐
│   已确认        │  已发送,未确认     │  可立即发送        │  还不能发送        │
│   (可回收)      │  (空中飞行)       │  (窗口内,未发出)   │  (窗口外)         │
├────────────────┼──────────────────┼──────────────────┼──────────────────┤
↑                ↑                  ↑                  ↑
0           LastByteAcked      SendBase          LastByteSent
             (或 SendBase−1)  (=LastByteAcked+1)

窗口右边界 = SendBase + min(cwnd, rwnd)
窗口范围从 SendBase 开始，长度 = min(cwnd, rwnd)
```

- **LastByteAcked 之前**：已确认，缓冲区空间可以回收
- **SendBase → LastByteSent**：已发出但尚未确认
- **LastByteSent → 窗口右边界**：窗口允许发送但尚未发出的数据
- **窗口右边界之外**：应用已写入但暂时不允许发送——被 cwnd 或 rwnd 卡住

### 发送窗口约束（Kurose §3.7）

发送方必须遵守（来自拥塞控制章节）：

$$\text{LastByteSent} - \text{LastByteAcked} \leq \min(\text{cwnd}, \text{rwnd})$$

即**在空中飞行的数据量**不能超过发送窗口。发送窗口是 `cwnd`（拥塞控制）和 `rwnd`（流量控制）中更紧的那个约束——它是可靠传输、流量控制、拥塞控制三者的**共同执行点**。

当 ACK 到达推动 `LastByteAcked` 前进时，窗口随之向右滑动，为新的数据释放空间。如果新 ACK 还携带了更新的 `rwnd`，窗口大小也同步调整。

### 与 cwnd 和 rwnd 的关系

发送窗口是唯一**直接控制发送速率**的变量。cwnd 增大需要靠收到 ACK（证明网络能承受），rwnd 增大靠接收方通告（证明接收方消化了数据）——但最终都是通过发送窗口来体现：

- cwnd 缩小（丢包）→ 发送窗口缩小 → 空中数据量受限 → 发送速率降低
- rwnd 缩小（接收方忙）→ 发送窗口缩小 → 同上
- cwnd 和 rwnd 都很大 → 发送窗口由应用数据量决定 → 无闲置则满速发送

> **关键洞察**：TCP 的三个核心功能（可靠传输、流量控制、拥塞控制）在发送方汇合于同一个发送窗口。重传定时器关联的是窗口最左侧的 `SendBase`，流量控制限制窗口不会超过 `rwnd`，拥塞控制限制窗口不会超过 `cwnd`。

## TCP 发送方的事件

TCP 发送方处理三种主要事件：

### 1. 从应用层接收数据

TCP 从应用层接收数据，将其封装为报文段并传递给网络层。每个报文段包含一个序号——即该报文段首字节的序号。如果定时器尚未运行，启动定时器（定时器与最旧未确认字节相关联）。

### 2. 超时

TCP 通过重传引起超时的报文段来响应超时事件——该报文段是最旧未确认的报文段。然后 TCP **将超时间隔加倍**——这是一种**指数退避**机制。例如，初始超时间隔为 1.0 秒（TimeoutInterval 推荐最小值为 1 秒），第一次超时后将定时器设为 2.0 秒，如果再次超时设为 4.0 秒。每次从应用层接收数据并重新启动定时器时，超时间隔从最近的 [[TCP往返时间估计|EstimatedRTT 和 DevRTT]] 重新计算，而非使用翻倍后的值。

### 3. 收到 ACK

当 TCP 发送方收到 ACK 时，发生以下操作：

- **累积确认处理**：将 ACK 的值 $y$ 与 `SendBase` 比较。由于 TCP 使用累积确认，$y$ 确认了区间 $[SendBase,\; y-1]$ 内的所有字节（32 位序号空间下通常用普通数值比较即可，理论上需用 $\text{in\_range}$ 判定——详见 [[GBN#基于范围的序号|GBN 的序号范围讨论]]）。如果 $y$ 确认了新的数据（即 $\text{in\_range}(y-1,\; SendBase,\; \infty)$），更新 `SendBase = y`
- **重复 ACK 计数**：如果收到一个 ACK 且其值等于之前的 ACK 值（即重复 ACK），递增重复 ACK 计数
- **快速重传**：如果相同值的重复 ACK 计数达到 **3**，TCP 不等超时立即执行**快速重传（fast retransmit）**——重传被该 ACK 指示的丢失报文段

### 超时 vs 快速重传

| | 超时 | 快速重传（3 dup ACK） |
|---|------|---------------------|
| 触发条件 | 定时器超时 | 收到 3 个相同 ACK 值的重复 ACK |
| 响应 | 重传 + 超时间隔加倍 | 立即重传，不等超时 |
| 隐含的严重程度 | 严重拥塞 | 轻微拥塞 |

## TCP 确认生成策略

接收方遵循以下 ACK 生成规则（RFC 5681）：

| 事件 | TCP 接收方动作 |
|------|---------------|
| 期望序号的报文段按序到达，且之前期望序号的所有数据已被确认 | **延迟 ACK**——等待最多 500 ms 看是否有下一个报文段到达。如果没有，发送 ACK |
| 期望序号的报文段按序到达，且之前有一个报文段的 ACK 尚未发送 | 立即发送**单个累积 ACK**，确认两个按序报文段 |
| 序号大于期望序号的失序报文段到达——检测到了间隔 | 立即发送**重复 ACK**，指示期望序号的字节 |
| 部分或完全填充了接收数据间隔的报文段到达 | 如果该报文段从间隔的低端开始，立即发送 ACK |

### 延迟 ACK 的影响

延迟 ACK（通常最多 500 ms）减少网络中的 ACK 报文段数量，但也影响 TCP 行为：

- **慢启动增速放缓**：cwnd 每收到一个 ACK 增加 1 MSS——ACK 越少，cwnd 增长越慢。RFC 5681 规定慢启动期间使用**每报文段确认字节数**而非每 ACK 计数来补偿。
- **与 Nagle 算法的交互**：Nagle 算法在未收到 ACK 前不发送小报文段，延迟 ACK 则延迟发送 ACK——两者同时启用可能导致 200–500 ms 的短暂死锁。现代实现通过启发式规则（如仅对全尺寸报文段启用 Nagle）缓解此问题。
- **捎带确认（Piggybacking）**：如果接收方在 500 ms 内有数据要回传，ACK 可搭载在数据报文段上一起发送，节省带宽。

## 快速重传的机制

假设发送方发送了序号为 0、1000、2000、3000、4000 的报文段。序号 0 的报文段被接收并确认（ACK 1000）。但序号 1000 的报文段丢失。接收方收到序号 2000 的失序报文段时，立即发送一个重复的 ACK——ACK 的值仍然是 1000（期望收到序号 1000 的数据）。随后序号 3000 和 4000 的报文段到达，接收方再发送两个重复的 ACK 1000。

发送方收到第三个重复 ACK 1000 后，不等超时就**立即重传**序号 1000 的报文段。这就是**快速重传**——在定时器超时之前就检测到丢包并重传，大大减少了等待时间。
