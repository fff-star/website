# 流式存储视频

> 参考：Kurose §9.2

**流式存储视频（Streaming Stored Video）**是指预先录制并存储在服务器上的视频，客户端通过因特网边下载边播放（而不是完全下载后再播放）。YouTube 和 Netflix 是典型例子。核心机制是**客户端缓冲（client-side buffering）**——在开始播放前预先积累若干秒的视频数据，以吸收网络传输的波动。

## UDP 流

早期的视频流方案（如 RealNetworks 的 RealPlayer）使用 [[UDP]] 传输，理由如下：

- TCP 的可靠重传会导致播放停顿——视频播放有时序要求，已错过的帧即使重传也无用
- UDP 不重传，丢失的帧直接跳过（对用户影响可接受）

UDP 流的工作方式：
1. 服务器以**与客户端视频消耗速率匹配的速率**通过 UDP 发送视频块
2. 速率由独立于 UDP 的**控制协议**（如 RTSP）管理
3. 客户端通常维护一个小的**客户端缓冲区**（仅容纳几秒视频），用于平滑网络抖动

### UDP 流的问题

- **防火墙穿透困难**：许多防火墙默认阻止非标准端口的 UDP 流量
- **缺乏拥塞控制**：UDP 不会因网络拥塞减速，可能挤占 TCP 流量，被网络管理员封锁
- **控制协议复杂**：需要额外的 RTSP 等协议管理播放控制（暂停/快进/回退）

由于这些问题，UDP 流已被**HTTP 流**（即 TCP 流）大规模取代。

## HTTP 流

HTTP 流将视频视为普通的 HTTP 对象（如文件），使用 TCP 传输。这是目前视频流的主流方式。

### 工作原理

1. 视频作为普通文件存储在 HTTP 服务器上，有一个 URL
2. 客户端与服务器建立 TCP 连接，发送 HTTP GET 请求
3. 服务器在 TCP 连接上以**尽可能快的速率**发送视频数据（受 TCP 拥塞控制限制）
4. 客户端接收数据存入**客户端应用缓冲区**
5. 当缓冲区积累到预定的**填充水平**（如 5 秒视频），客户端开始播放
6. 播放期间，客户端持续从缓冲区取出视频帧，同时后台继续从 TCP 接收数据填充缓冲区

### 客户端缓冲的作用

客户端缓冲解决**网络吞吐量波动**问题：

- 如果 TCP 交付速率暂时低于播放速率 → 缓冲区水位下降，但播放不中断
- 如果 TCP 交付速率重新超过播放速率 → 缓冲区被重新填充
- 只有当缓冲区**完全排空**时播放才会停顿（rebuffering）

缓冲容量越大，抗网络波动的能力越强，但初始等待时间越长。

### 早期 HTTP 流的局限

- 所有用户收到相同编码版本，无论其可用带宽如何。低带宽用户频繁停顿，高带宽用户浪费带宽
- 需要**自适应流**解决此问题

## DASH（自适应流）

DASH（Dynamic Adaptive Streaming over HTTP）的详细内容见 [[视频流与CDN]]。此处简要概括核心思想：

1. 视频编码为多个不同比特率版本
2. 每个版本切分为秒级**块（chunk）**
3. 客户端维护**清单文件**，列出各版本的 URL
4. 客户端动态测量可用带宽，为每个块选择最合适的版本

DASH = HTTP 流 + 自适应 + 分段。这已被所有主流视频平台采用。
