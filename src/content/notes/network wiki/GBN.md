# GBN（回退 N 步）

> 参考：Kurose §3.4.4

**回退 N 步（Go-Back-N, GBN）**是流水线可靠数据传输的两种基本方法之一。GBN 允许发送方发送多个分组而不等待确认，但限制了流水线中最大未确认分组的数量不得超过某个最大值 $N$——**窗口大小（window size）**。

## 基于范围的序号

GBN 协议使用**基于范围**的序号表示。如果分组首部中的序号字段为 $k$ 位，则序号范围为 $[0, 2^k - 1]$。所有涉及序号的操作使用**模 $2^k$ 算术**。GBN 窗口大小的最大值为 $2^k - 1$（防止发送方序号空间回绕导致旧分组与新分组混淆——发送方重传整个窗口后，接收方的累积确认需要能唯一区分旧窗口和新窗口的分组）。

### 范围判定：模运算下的「属于」

由于序号空间是环形的（$2^k-1$ 之后绕回 $0$），不能用普通的数值不等号判断"在窗口内"。正确的方式是**基于范围的判定**：

$$ \text{in\_range}(a, low, high) = \begin{cases} low \leq a \leq high & \text{若 } low \leq high \\ a \geq low \;\lor\; a \leq high & \text{若 } low > high \text{（回绕）} \end{cases} $$

其中 $low$ 和 $high$ 是模 $2^k$ 下的序号值。当 $low > high$ 时区间跨越了 $2^k-1 \to 0$ 的边界。

**示例**：$k=2$（序号 $0,1,2,3$），$send\_base=3$，窗口 $N=3$，则窗口区间为 $[3, (3+2)\bmod 4] = [3, 1]$（回绕）。序号 1 在窗口内吗？

> $low=3$, $high=1$, $low > high$ → 回绕 → $\text{in\_range}(1,3,1)$：$1 \geq 3$？否。$1 \leq 1$？是 → ✓
> $\text{in\_range}(2,3,1)$：$2 \geq 3$？否。$2 \leq 1$？否 → ✗

所以序号 0、1 属于当前窗口，序号 2 不在窗口内。

## 发送方

发送方维护三个变量：

- **send_base**：最早未确认分组的序号（窗口的左边界）
- **nextseqnum**：下一个可用的尚未使用的序号——即将发送的下一个分组的序号
- **窗口大小 $N$**

GBN 发送方处理以下事件：

1. **上层调用**：如果窗口未满——即 $\text{in\_range}(nextseqnum,\; send\_base,\; (send\_base + N - 1) \bmod 2^k)$——创建并发送分组，$nextseqnum$ 更新为 $(nextseqnum + 1) \bmod 2^k$；否则拒绝上层的数据（或缓冲后等待窗口腾出空间）
2. **收到 ACK**：GBN 使用**累积确认（cumulative acknowledgment）**。序号为 $n$ 的 ACK 确认了区间 $[send\_base,\; n]$ 内的**所有**分组（模 $2^k$ 范围内的 $\text{in\_range}$ 意义下）。发送方将 $send\_base$ 更新为 $(n + 1) \bmod 2^k$，并重置定时器（对新的 $send\_base$ 对应的分组启动）
3. **超时**：发送方仅对**最旧未确认的分组**（序号 $send\_base$）维护**单个定时器**。如果定时器超时，发送方**重传窗口中的所有未确认分组**——即序号在 $[send\_base,\; (nextseqnum - 1) \bmod 2^k]$ 区间内的所有分组

累积确认的关键性质：ACK $n$ 隐含确认了从 $send\_base$ 到 $n$ 的全部序号。这意味着即使中间某个 ACK 丢失了（例如 ACK 2 丢了但 ACK 3 到了），发送方直接通过 ACK 3 就确认了 2 和 3 两个分组——不需要等到 ACK 2 到达。因为 $\text{in\_range}(2,\; send\_base,\; 3)$ 成立，序号 2 落在被 ACK 3 覆盖的区间内。这使得 GBN 对 ACK 丢失有一定容忍度。

## 接收方

GBN 接收方的逻辑极其简单：

- 如果收到**按序**的分组（序号恰好是期望的 `expectedseqnum`），接收方提取数据交付上层，发送一个 ACK（ACK 序号 = 收到的分组序号），将 `expectedseqnum` 递增 1
- 如果收到**失序**的分组（不是 `expectedseqnum`），接收方**直接丢弃**该分组，然后重新发送**最近正确接收的分组的 ACK**（即 ACK `expectedseqnum - 1`）

关键点：**GBN 接收方从不缓存失序分组**。接收方只需要维护一个变量 `expectedseqnum`——它期望的下一个分组序号。由于接收方简单地丢弃失序分组，任何丢失分组的重传将导致接收方丢弃从丢失点之后的所有（重新按序到达的）分组。

## GBN 的运行机制

![GBN与SR窗口行为对比](diagrams/gbn_vs_sr.png)

以下用一个具体的时间线演示 GBN 在丢包场景下如何工作。假设窗口大小 $N=4$。

### 初始状态

发送方：`send_base = 0`，`nextseqnum = 0`，窗口范围 $[0, 3]$
接收方：`expectedseqnum = 0`

### 完整时间线

```
发送方                               接收方              expectedseqnum
  │                                    │
  │── pkt0 ────────────────────────▶  │ ✓ 按序到达        0→1
  │── pkt1 ──────────[丢失]─────────  │                   1
  │── pkt2 ────────────────────────▶  │ ✗ 失序！期望1收到2  1
  │── pkt3 ────────────────────────▶  │ ✗ 失序！期望1收到3  1
  │                                    │
  │◀── ACK0 ─────────────────────────│ 接收方确认 pkt0
  │◀── ACK0 ─────────────────────────│ 失序时重发 ACK0
  │◀── ACK0 ─────────────────────────│ 失序时重发 ACK0
  │                                    │
  │ 收到 ACK0 → send_base=1           │
  │ 现在可以发 pkt4                    │
  │── pkt4 ────────────────────────▶  │ ✗ 失序！期望1收到4  1
  │                                    │
  │ ⏰ 定时器超时！                    │
  │ 重传未确认的: pkt1,pkt2,pkt3,pkt4 │
  │                                    │
  │── pkt1(R) ─────────────────────▶  │ ✓ 按序！交付       1→2
  │── pkt2(R) ─────────────────────▶  │ ✓ 按序！交付       2→3
  │── pkt3(R) ─────────────────────▶  │ ✓ 按序！交付       3→4
  │── pkt4(R) ─────────────────────▶  │ ✓ 按序！交付       4→5
  │                                    │
  │◀── ACK4 ─────────────────────────│ 累积确认：0~4 全部收到
  │ 收到 ACK4 → send_base=5          │
```

### 逐步解读

**① 正常发送（pkt0~pkt3）**

发送方窗口 $[0,3]$ 未满，连续发出 4 个分组。pkt0 正常到达，接收方交付、发 ACK0，`expectedseqnum` 变为 1。

**② 丢包（pkt1 丢失，pkt2~pkt4 失序）**

pkt1 丢了，但 pkt2、pkt3 继续到达。接收方期望的是 1 号，发现收到的是 2 → **直接丢弃**，并重复发送 ACK0（最后一次正确收到的是 0 号）。pkt3、pkt4 同样被丢弃，每次丢弃都重发 ACK0。

这里体现了 GBN 接收方的核心原则：**不缓存任何失序分组**。即使 pkt2、pkt3、pkt4 完好无损地到达了，接收方照样扔掉——"我只要按序的。"

**③ 累积确认（ACK0）**

发送方收到 ACK0 后，`send_base` 变为 1。注意：此时即使后续 pkt2~pkt4 还没被确认，窗口右边界也向右滑动了一个位置，pkt4 得以发送。

**④ 超时重传**

整个窗口中只有 pkt0 被确认了（send_base=1），pkt1~pkt4 都没收到对应的 ACK。定时器超时后，发送方**一次性重传窗口中全部未确认的分组**：pkt1、pkt2、pkt3、pkt4。这是 GBN 名称的由来——从丢包点开始"回退 N 步"，全部重来。

**⑤ 累积确认收尾**

重传后所有分组按序到达，接收方依次交付。它发出的最终 ACK 序号是 4（最后一个正确收到的分组），但因为 GBN 使用累积确认，ACK 4 **同时隐含确认了 0、1、2、3、4 全部**。发送方收到 ACK 4 后，`send_base` 直接跳到 5，窗口清空。

### 关键观察

- 即使只有 **1 个**分组（pkt1）丢了，发送方重传了 **4 个**分组（pkt1~pkt4）。这就是 GBN 在差错率高时效率低的原因。
- 接收方发出的多个 ACK0 是冗余的——只要有一个到达发送方，累积确认就生效了。但如果全部丢失，定时器最终也会兜底。

## GBN 的优缺点

优点：
- 接收方简单——不需要缓存，不需要对失序分组排序
- 适合低差错率的情况——丢包代价只是几个分组需要重传

缺点：
- 丢包或差错后需要大量不必要的重传——即使只有一个分组丢失，窗口中的所有未确认分组都会被重传
- 浪费带宽——接收方正确地收到了失序分组但全部丢弃
