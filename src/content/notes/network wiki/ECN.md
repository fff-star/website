# ECN（显式拥塞通知）

> 参考：RFC 3168; Kurose §3.7.1

**显式拥塞通知（Explicit Congestion Notification, ECN）** 是 TCP/IP 中的一种拥塞控制扩展。它在 RFC 3168 中定义，允许路由器在分组通过时 **标记**（而非丢弃）分组来指示拥塞，从而让发送方在丢包发生之前就减速。

## 动机：丢包作为拥塞信号的弊端

传统的 TCP 拥塞控制依赖**丢包**作为拥塞信号——超时或三个重复 ACK 才能检测到拥塞。这种方法有两个问题：

1. **反应性而非前瞻性**：丢包已经是拥塞的结果，发送方在拥塞发生后才能反应
2. **不必要的丢包**：丢包需要重传，增加了延迟和带宽浪费，对时延敏感的应用（如网页浏览、视频会议）尤其有害

ECN 的核心思想：路由器在队列即将满时**标记分组**（在 IP 首部中设置拥塞指示），而非直接丢弃——发送方在丢包发生**之前**就得知拥塞，主动减速。

## ECN 在 IP 和 TCP 层的实现

ECN 涉及网络层和运输层的配合：

### IP 层的 ECN 字段

IPv4 和 IPv6 首部中使用 TOS / Traffic Class 字段中的 2 个比特：

| 值 | 名称 | 含义 |
|----|------|------|
| 00 | Not-ECT | 不支持 ECN |
| 01 | ECT(1) | 支持 ECN，与 ECT(0) 等价于"支持 ECN" |
| 10 | ECT(0) | 支持 ECN，与 ECT(1) 等价于"支持 ECN" |
| 11 | CE（Congestion Experienced）| 端点经历了拥塞 |

### TCP 层的 ECN 标志

TCP 首部中增加了两个标志位：

- **CWR（Congestion Window Reduced）**：发送方告知接收方"我已减小了拥塞窗口"
- **ECE（ECN Echo）**：接收方告知发送方"我收到了拥塞指示"

### ECN 的工作流程

1. **协商**：TCP 三次握手时，发送方在 SYN 中设置 ECE + CWR，接收方在 SYN+ACK 中设置 ECE（不设 CWR），确认双方支持 ECN
2. **数据传输**：发送方每次发送报文段时在 IP 首部中标记 ECT（0 或 1）——表示端点支持 ECN
3. **路由器标记**：启用了 ECN 的路由器在检测到拥塞时（通常通过 RED 等主动队列管理算法），将 CE 位置 1，而非丢弃分组
4. **接收方通知**：接收方收到 CE 标记的分组后，在下一个 TCP ACK 中设置 **ECE 标志**——即使分组未被丢弃也通知发送方
5. **发送方响应**：发送方收到 ECE 标记的 ACK 后，**像检测到丢包一样将 cwnd 减半**，并在下一个报文段中设置 **CWR** 标志——告知接收方已减窗

## ECN 与 AQM（主动队列管理）

ECN 通常与**主动队列管理（Active Queue Management, AQM）**算法配合使用。

**RED（Random Early Detection）**是经典的 AQM 算法。RED 维护队列的**加权平均长度**：

- 当平均队列长度 < 最小阈值：不标记也不丢弃
- 当最小阈值 ≤ 平均队列长度 < 最大阈值：以一定概率随机标记（或丢弃）分组
- 当平均队列长度 ≥ 最大阈值：标记（或丢弃）所有分组

RED 的随机早期标记使发送方在队列真正溢出**之前**就减速——这就是"早期"的含义。与传统尾丢弃（Tail Drop）不同，RED ± ECN 避免了**全局同步（global synchronization）**——即大量 TCP 连接同时发现丢包、同时减窗、同时恢复导致吞吐量剧烈振荡。

## ECN 的好处

- **避免不必要的丢包**：分组被标记而非丢弃，不需要重传
- **降低延迟**：发送方在队列溢出前减速，队列长度保持较低水平
- **改善吞吐量**：减少重传浪费的带宽，提高有效吞吐量
- **适用于时延敏感应用**：Web 浏览、实时通信等受益于低延迟

目前 ECN 已在因特网中逐步部署，数据中心网络和云服务中已广泛启用。
