# TCP 流量控制

> 参考：Kurose §3.5.5

TCP 的**流量控制（flow control）**服务旨在消除发送方溢出接收方缓冲区的可能性——即发送方发送数据的速率不能超过接收方处理数据的速率。流量控制与拥塞控制是不同的机制：流量控制关注的是**接收方的能力**，拥塞控制关注的是**网络的能力**。

## 接收窗口

TCP 通过让发送方维护一个称为**接收窗口（receive window, rwnd）**的变量来实现流量控制。rwnd 告知发送方：接收方当前还有多少可用的缓冲区空间。

接收方在每个报文段中向发送方通告其接收窗口——通过 TCP 报文段首部中的**接收窗口字段（16 比特）**。发送方确保其未确认的数据量不超过 rwnd：

$$\text{LastByteSent} - \text{LastByteAcked} \leq \text{rwnd}$$

## 接收窗口的计算

接收方维护两个变量：

- **LastByteRead**：应用进程从 TCP 接收缓冲区中读取的最后一个字节的编号
- **LastByteRcvd**：从网络到达并已放入 TCP 接收缓冲区的最后一个字节的编号

接收方可用的缓冲区空间为：

$$\text{rwnd} = \text{RcvBuffer} - (\text{LastByteRcvd} - \text{LastByteRead})$$

当接收方通告 rwnd 时，发送方相应地限制其未确认数据的量。如果接收方的应用进程读取数据速度慢于数据到达速度，rwnd 会减小——从而限制发送方的发送速率。如果应用进程读取速度很快，rwnd 保持较大——发送方可以更快地发送数据。

## rwnd = 0 时的死锁问题

当 rwnd = 0 时，发送方停止发送数据。问题是：如果接收方的应用进程随后读取了数据使得 rwnd > 0，但接收方并没有数据要发送给发送方（因此无法承载更新后的 rwnd），发送方就永远不知道 rwnd 已经恢复——这就是**死锁**。

为了解决这个问题，TCP 规范要求：当接收窗口为 0 时，发送方**定期发送只有一个字节数据的探测报文段（persist timer）**。这些探测报文段会被接收方确认，ACK 中携带更新后的 rwnd。一旦 rwnd 重新变为非零值，发送方即可恢复发送。这种机制防止了死锁。

## 流量控制与拥塞控制的区别

| | 流量控制 | 拥塞控制 |
|---|---------|---------|
| 限制变量 | rwnd（接收方通告） | cwnd（发送方估计） |
| 防止 | 接收方缓冲区溢出 | 网络链路和路由器过载 |
| 信息来源 | 来自接收方（报文段首部） | 来自网络（通过丢包/延迟推断） |
| 实际发送窗口 | $\min(\text{cwnd}, \text{rwnd})$ | $\min(\text{cwnd}, \text{rwnd})$ |

实际的发送窗口大小是 cwnd 和 rwnd 的**最小值**——发送方既要尊重接收方的处理能力，也要尊重网络容量。
