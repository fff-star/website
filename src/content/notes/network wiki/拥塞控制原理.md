# 拥塞控制原理

> 参考：Kurose §3.6

拥塞控制是计算机网络中与可靠数据传输同等重要的基本问题。当网络中某个节点接收到的数据超过其转发能力时，数据分组在路由器缓冲区中堆积排队；当缓冲区溢出时分組被丢弃。丢失导致发送方重传——重传加剧网络负载，可能引发正反馈环路，最终导致**拥塞崩溃（congestion collapse）**。

## 拥塞的原因与代价

### 场景 1：两个发送方，无限缓冲区的路由器

考虑一个最简单的拥塞场景：两个主机（A 和 B）各有一条无限容量的链路连接到一台路由器，该路由器通过一条出链路（容量 $R$）连接到目的地。

- A 和 B 共享出链路（速率 $R$）
- 每连接的吞吐量曲线：当发送速率较低时，吞吐量与发送速率相等（收到的 = 发送的）
- 当发送速率接近 $R/2$ 时，吞吐量接近 $R/2$——出链路由两方公平共享
- 一旦达到容量上限，继续增大发送速率不会提高端到端吞吐量——**吞吐量受限于共享链路容量**
- 然而，分组在路由器中的**排队时延急剧增长**——这是拥塞的第一个代价：**大排队时延**

### 场景 2：两个发送方，有限缓冲区的路由器（增加重传）

在场景 1 的基础上：路由器拥有**有限缓冲区**。当缓冲区满时，到达的分组被丢弃。TCP 发送方通过重传丢失的分组来提供可靠传输。

由于重传，现在到达出链路的**总速率大于原来的输入速率**——相同的原始数据可能被传输多次。用 $\lambda_{in}$ 表示初始数据（不包括重传）的传输速率，$\lambda_{out}$ 表示到达出链路的总速率（包括重传）。即使在 $R/2$ 边界上，$\lambda_{out}$ 仍可能高于 $R/2$——因为重传的流量占用了一部分出链路容量。这是拥塞的第二个代价：**发送方为补偿丢包而进行的重传浪费了上游传输资源**。

在最坏情况下：分组在即将到达路由器时被丢弃——上游路由器为该分组（在它被丢弃之前）所做的所有传输工作都被浪费了。这是拥塞的第三个代价：**在距离目的地仅一跳时丢包，上游所有传输努力被浪费**。

### 场景 3：四个发送方，多跳路径与路由器

在更复杂的多跳路径场景中（四个发送方通过两台路由器共享两条链路），拥塞问题进一步恶化：

- 当一个连接丢弃的分组**在接近目的地时被丢弃**，所有上游路由器为传输该分组所做的工作被完全浪费
- 连接之间的交互可能导致**不公平分配**——某些连接经历更多丢包，它们的吞吐量受到不合理惩罚

## 拥塞控制的两大类方法

拥塞控制的方法大致可分为两大类：

### 端到端拥塞控制

端到端方法中，网络层**不为拥塞控制提供显式反馈**。端系统通过观察网络行为（分组丢失和延迟）来**推断**网络中是否存在拥塞。TCP 的拥塞控制属于这一类——TCP 发送方通过**丢包（超时或三个重复 ACK）作为拥塞的信号**，自动降低其发送速率。这是因特网当前使用的方法。

### 网络辅助拥塞控制

网络辅助方法中，**路由器向端系统提供有关网络拥塞状态的显式反馈**。反馈的形式可以是：

- **直接反馈**：拥塞的路由器直接向发送方发送一个"拥塞通知"分组
- **标记分组**：路由器在数据分组中标记一个比特（如 IP 首部中的 ECN——显式拥塞通知），接收方在 ACK 中将此信息回传给发送方

ATM ABR（Available Bit Rate）拥塞控制是网络辅助方法的经典例子——交换机向发送方提供显式的速率反馈。

## 拥塞控制与流量控制的区别

| | 拥塞控制 | 流量控制 |
|---|---------|---------|
| 目的 | 防止发送方淹没**网络** | 防止发送方淹没**接收方** |
| 关注对象 | 网络容量、路由器缓冲区 | 接收方缓冲区 |
| 反馈来源 | 网络中的丢包/延迟 | 接收方通告的 rwnd |
| 机制 | AIMD、慢启动等 | 滑动窗口（rwnd） |
